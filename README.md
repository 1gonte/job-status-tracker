
# Job Status Tracker

REST API для регистрации заданий, управления их статусами и получения статистики.

Проект разработан на Python с использованием FastAPI в рамках итоговой работы по курсу "Инфраструктура и администрирование".

## Возможности

- Создание заданий с именем, автором, описанием и категорией.
- Получение списка заданий с фильтрацией по статусу.
- Получение задания по идентификатору.
- Изменение статуса с проверкой разрешённых переходов.
- Получение статистики по статусам, категориям и авторам.
- Проверка работоспособности и версии приложения.
- Настройка через переменные окружения.
- Логирование основных событий.
- Автоматические тесты на pytest.
- CI с GitHub Actions и сохранением отчёта о тестировании.

Приложение управляет метаданными заданий, но не выполняет сами задания.

## Установка и запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/1gonte/job-status-tracker.git
cd job-status-tracker
```

### 2. Создание виртуального окружения

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Установка зависимостей

```bash
python -m pip install -r requirements.txt
```

Для запуска автоматических тестов дополнительно:

```bash
python -m pip install -r requirements-dev.txt
```

### 4. Настройка переменных окружения

Создайте файл `.env` на основе примера:

```bash
cp .env.example .env
```

Доступные параметры:

| Параметр | Значение по умолчанию | Описание |
|----------|-----------------------|----------|
| APP_NAME | Job Status Tracker | Название приложения |
| LOG_LEVEL | INFO | Уровень логирования |
| MAX_JOBS | 100 | Максимальное количество заданий |

Поддерживаемые уровни логирования: `DEBUG`, `INFO`, `WARNING`.

Если значение `LOG_LEVEL` или `MAX_JOBS` некорректно, используется значение по умолчанию и записывается предупреждение.

### 5. Запуск приложения

```bash
uvicorn app_final:app --reload
```

Приложение будет доступно по адресу:

http://127.0.0.1:8000

Интерактивная документация Swagger UI:

http://127.0.0.1:8000/docs

Альтернативная документация ReDoc:

http://127.0.0.1:8000/redoc

## API

| Метод | Endpoint | Назначение |
|-------|----------|------------|
| GET | /health | Проверка работоспособности |
| GET | /version | Получение версии |
| POST | /jobs | Создание задания |
| GET | /jobs | Получение списка заданий |
| GET | /jobs/{job_id} | Получение задания по ID |
| PATCH | /jobs/{job_id}/status | Изменение статуса |
| GET | /stats | Получение статистики |

### Создание задания

```bash
curl -X POST http://127.0.0.1:8000/jobs \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Data processing",
    "author": "George",
    "description": "Process input dataset",
    "category": "data_processing"
  }'
```

При успешном создании возвращается HTTP 201 и объект задания.

Каждое новое задание автоматически получает:
- уникальный последовательный ID;
- статус `pending`;
- время создания `created_at` в UTC.

Обязательные поля: `name`, `author`.

Допустимые категории:
- `data_processing`
- `ml_inference`
- `report_generation`
- `other`

Категория по умолчанию — `other`.

### Получение заданий

```bash
curl http://127.0.0.1:8000/jobs
```

Фильтрация по статусу:

```bash
curl "http://127.0.0.1:8000/jobs?status=running"
```

Получение одного задания:

```bash
curl http://127.0.0.1:8000/jobs/1
```

### Изменение статуса

```bash
curl -X PATCH http://127.0.0.1:8000/jobs/1/status \
  -H "Content-Type: application/json" \
  -d '{"status": "running"}'
```

Допустимые переходы:

```text
pending -> running

running -> completed
running -> failed

completed -> terminal state
failed -> terminal state
```

Повторная установка текущего статуса разрешена и возвращает HTTP 200.

Запрещённые переходы возвращают HTTP 409.

### Получение статистики

```bash
curl http://127.0.0.1:8000/stats
```

Пример ответа:

```json
{
  "total_jobs": 2,
  "by_status": {
    "pending": 1,
    "running": 1,
    "completed": 0,
    "failed": 0
  },
  "by_category": {
    "data_processing": 1,
    "ml_inference": 0,
    "report_generation": 0,
    "other": 1
  },
  "by_author": {
    "George": 2
  }
}
```

Статистика пересчитывается при каждом запросе.

## Обработка ошибок

API использует стандартные HTTP-коды:

| Код | Описание |
|-----|----------|
| 200 | Успешный запрос |
| 201 | Задание успешно создано |
| 404 | Задание не найдено |
| 409 | Запрещённый переход или превышение MAX_JOBS |
| 422 | Некорректные входные данные |

## Хранение данных

Задания хранятся в оперативной памяти в словаре Python.

Ограничения реализации:
- Данные теряются после перезапуска приложения.
- База данных не используется.
- Выполнение фоновых заданий не реализовано.
- Приложение рассчитано на один серверный процесс.

Лимит `MAX_JOBS` распространяется на все зарегистрированные задания независимо от их статуса.

## Логирование

Используется логгер `job_status_tracker`.

Основные уровни сообщений:

- `INFO` — создание задания и успешное изменение статуса.
- `DEBUG` — повторная установка текущего статуса, запросы `/health` и `/version`.
- `WARNING` — запрещённые переходы, превышение лимита и некорректная конфигурация.

## Автоматическое тестирование

Тесты находятся в файле `test_app.py`.

Запуск:

```bash
python -m pytest -v test_app.py
```

Реализованные проверки:

1. Проверка `/health`.
2. Успешное создание задания.
3. Валидация некорректного имени.
4. Запрещённый переход статуса.
5. Успешные переходы статусов.
6. Корректность агрегированной статистики.
7. Ограничение `MAX_JOBS`.

Перед каждым тестом in-memory-хранилище сбрасывается с помощью pytest fixture.

## CI/CD

В проекте настроен GitHub Actions workflow:

`.github/workflows/ci.yml`

Workflow запускается при:
- `push`;
- `pull_request`.

При запуске выполняются:
1. Получение исходного кода.
2. Настройка Python.
3. Установка зависимостей.
4. Запуск pytest.
5. Сохранение текстового отчёта в артефакт `pytest-results`.
